## 1. React и `@wordpress/components`: плюсы, минусы и рекомендация

### Короткий ответ

Использовать React-компоненты WordPress **нормально и уместно**. Это официальный инструментарий WordPress, а не чужой UI-фреймворк. WordPress сам предоставляет `wp-element` (слой над React), `wp-components`, `wp-i18n`, `wp-data` и другие пакеты. При правильной сборке они не включаются второй копией в плагин: `@wordpress/scripts` / dependency extraction превращает импорты в зависимости WordPress и генерирует `.asset.php`.

То есть главные страхи «React раздует ZIP» и «плагин привезёт свою копию React» **не относятся к правильной реализации**.

### Плюсы

1. **Красивый нативный WordPress-интерфейс.** `Button`, `ToggleControl`, `SelectControl`, `TextControl`, `ColorPalette`, `Notice`, `Modal`, `SearchControl`, `TabPanel`, `PanelBody`, `ComboboxControl` выглядят как часть WordPress, а не как отдельный сайт внутри админки.
2. **Сложная интерактивность без клубка jQuery.** Для конструктора групп, поиска товаров, сортировки, предпросмотра, зависимых полей и условных секций React существенно чище простого JS.
3. **Состояние формы.** Можно безопасно показать несохранённые изменения, отменить их, сбросить вкладку и проверить зависимости до сохранения.
4. **Доступность.** Стабильные компоненты WordPress уже умеют фокус, `aria-*`, подписи и клавиатурное управление лучше самодельных контролов.
5. **Переиспользование.** Одинаковые компоненты настройки кнопки, цвета, позиции, списка исключений и справки можно использовать в разных вкладках.
6. **Будущие блоки Gutenberg.** Опыт и часть компонентов пригодятся для блока сравнения в 1.3+.

### Минусы и реальные риски

1. **Сборочная цепочка.** Нужны исходники, `@wordpress/scripts`, собранный JS, `.asset.php` и воспроизводимая команда сборки. Ошибка в зависимостях может проявиться только на чистой странице WordPress.
2. **Разные версии компонентов в WP 6.6 и WP 7.1.** Плагин использует ту версию `wp-components`, которая встроена в конкретный WordPress. Новый prop может существовать на 7.1 и отсутствовать на 6.6.
3. **Экспериментальные компоненты нестабильны.** Всё с префиксом `__experimental` может менять API; официальная документация прямо предупреждает о breaking changes.
4. **JS становится обязательным.** Если скрипт не загрузился, полностью клиентская форма исчезнет. Нужен PHP-контейнер с понятной ошибкой, а не пустой экран.
5. **Двойная валидация.** Удобная клиентская проверка не заменяет PHP: `Settings::sanitize()` остаётся единственным источником правды.
6. **Стили WordPress не гарантируют красивый дизайн сами по себе.** Компоненты дают хорошие элементы, но красота зависит от структуры, ритма, ширины, группировки и аккуратного scoped CSS. «Взяли React» не равно «стало красиво».
7. **Тестирование.** Помимо PHP/WPCS нужны сборка admin bundle, проверка зависимостей, ошибки консоли и браузерные сценарии на WP 6.6 и 7.1.
8. **Каталог WordPress.org.** Если JS минифицирован, исходники и инструкции сборки должны быть доступны; никаких CDN или удалённого кода.

### Моя рекомендация: ограниченный React, а не React «везде»

1. PHP регистрирует страницу, проверяет `manage_woocommerce`, создаёт nonce, загружает текущие настройки и выводит корневой контейнер.
2. React рендерит только админский интерфейс настроек. Фронтенд магазина остаётся на лёгком vanilla JS, как сейчас.
3. Используем только **стабильные** компоненты WordPress. Любой `__experimental*` запрещён без отдельного решения и fallback.
4. Пакеты `@wordpress/*` externalized: runtime — встроенные `wp-element`, `wp-components`, `wp-i18n`, а не копии внутри bundle.
5. PHP `Settings::sanitize()` — единственный окончательный валидатор. React даёт мгновенную подсказку, но сервер перепроверяет всё.
6. Сохранение — обычный Settings API для простых полей, REST с nonce и тем же sanitizer для конструктора групп и поиска.
7. При сбое JS PHP-контейнер показывает понятное уведомление, а не пустоту.
8. Собственный CSS только scoped под `.rvn-compare-admin`; глобальные стили WordPress не переопределяем.
9. Исходники и команда сборки хранятся в рабочей области; собранные assets — в папке плагина. `node_modules` в плагин не попадает.
10. Перед выпуском — браузерные проверки admin UI на WP 6.6 и текущем WP.

При этих ограничениях React даст именно то, что вы хотите: красивую, современную админку без лишнего веса на витрине и без архитектурной ловушки. Моя прежняя рекомендация «PHP-формы по умолчанию» была слишком консервативной для объёма интерактивности старого ТЗ.

## 2. Что значит «drag-and-drop + стрелки для клавиатуры»

Предположим, администратор меняет порядок групп:

- мышью или пальцем он тянет группу за ручку `⋮⋮`;
- рядом у каждой строки есть кнопки **«Переместить вверх»** и **«Переместить вниз»**;
- до этих кнопок можно дойти клавишей Tab и нажать Enter/Space;
- после перемещения фокус остаётся на строке, а экранный диктор сообщает «Группа перемещена на позицию 2 из 5».

То есть «стрелки» — видимые кнопки со стрелками как альтернатива drag-and-drop, а не сложное сочетание клавиш. Это недорого, понятно и закрывает доступность. Оставить стоит.

## 3. Раздел C — все 11 выпавших отложенных функций

Вы правы: в прошлом чек-листе я спросил только про B и D, а про C не дал ни вопросов, ни рекомендаций. Это был мой недочёт.

### C1. Конструктор шорткодов в «Справке»

Форма, где администратор выбирает shortcode, аргументы и получает готовую строку с кнопкой «Копировать».

**Плюс:** полезно новичкам, снижает ошибки с кавычками и ID. **Минус:** нужно поддерживать синхронно с каждым новым аргументом. **Рекомендация:** вернуть в **1.1** вместе со справкой и дизайном.

### C2. «Добавить товар» — поиск и добавление

Старый план смешивал два сценария: администратор собирает статический shortcode; посетитель добавляет товар прямо на странице сравнения.

**Рекомендация:** админский поиск — **1.1**; посетительский «Добавить товар» — отдельно в **1.2/1.3**, только после макета.

### C3. Оформление вкладок категорий

Цвет, фон, текст, значок/emoji/миниатюра категории. **Плюс:** полезно магазинам с яркими категориями. **Минус:** легко получить пёструю таблицу. **Рекомендация:** **1.1**, progressive disclosure: по умолчанию только цвет; иконка/миниатюра — в «Расширенных».

### C4. Включение/исключение описаний значений атрибутов

Сейчас подсказки берутся из описаний терминов. Старый план позволял отключать их целиком, по атрибуту и по отдельному значению. **Рекомендация:** **1.1**, в расширенной секции: глобальный переключатель → список атрибутов → исключения значений при необходимости.

### C5. Произвольный SVG

**Плюс:** брендинг. **Минус:** SVG — активный формат и сложная поверхность XSS. **Рекомендация:** не делать загрузку в UI. В 1.3+ дать developer filter, принимающий уже очищенный SVG от кода разработчика. Администратору хватит встроенных иконок и emoji.

### C6. «Предпросмотр на сайте» с несохранёнными настройками

**Плюс:** реальный контекст темы лучше мини-превью. **Минус:** нужны временный token, capability, TTL, защита от кэша и утечки другим посетителям. **Рекомендация:** **1.2**, после дизайн-редактора; одноразовый подписанный token, `no-store`, только администратор.

### C7. Переопределение шаблонов в теме

**Плюс:** полная свобода разработчику темы. **Минус:** вечная совместимость устаревших копий, security fixes не доходят до override, а таблица у нас JS-driven. **Рекомендация:** убрать из плана; стабильные hooks/filters и CSS-классы лучше. Вернуть только по реальному запросу.

### C8. Авто-отступ плавающей шапки под липкую шапку темы

**Плюс:** панели не перекрываются. **Минус:** универсально определить чужую sticky header невозможно. **Рекомендация:** **1.2**: автоматическая попытка + ручной `scroll_offset_top` как гарантированный fallback; автоматика не перезаписывает ручное значение.

### C9. Классический виджет-обёртка

**Плюс:** старые классические темы. **Минус:** WordPress 6.6+ ориентирован на блоки; два UI для одной функции. **Рекомендация:** низкий приоритет **1.3+**, после Gutenberg-блока; убрать, если не будет реального запроса.

### C10. «Похожие товары» и «Недавно сравнивали»

Это разные функции: локальная история и алгоритм рекомендаций. **Рекомендация:** оставить на **1.3+ как два независимых отключаемых модуля**. Сначала «Недавно сравнивали» (localStorage, ограниченный список), потом «Похожие».

### C11. Статистика сравнения

**Плюс:** ценная аналитика ассортимента. **Минус:** противоречит архитектуре «без своих таблиц», затрагивает privacy/GDPR, cron, рост БД и производительность. **Рекомендация:** после 1.3 — отдельный opt-in модуль или отдельный RVN-плагин статистики, с retention и удалением данных.
