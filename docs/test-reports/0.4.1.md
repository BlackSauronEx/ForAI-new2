### Cache regression detail (`check.sh cache`, round B)

The scenario installs and configures WP Super Cache on `main` itself, then walks
through the full cached-page lifecycle: a real cache HIT before activation
(served without the button is the *proof* of caching), cache-file removal on
activation and on update, the first post-activation mobile request receiving the
button plus current CSS/JS, guest nonce recovery through a single un-cached AJAX
call with `private/no-store`, stale-nonce rejection followed by acceptance after
recovery, read-only nonce endpoint, cross-site request rejection, the retired old
`/session` REST route gone, the guest list surviving in the browser, signed-in
account handling (WordPress itself answers before our route), merge failure
keeping the guest list and successful merge clearing it, and zero JavaScript
errors in the browser. All 24 checks green; artifact `runs/cache-20260926-025300/`.

Level 1 (`main`) total run time: 64 s, six screenshots listed and not copied.
Level 2 `min` checks: tests 5 s, frontend 6 s, table 19 s, stand 21 s — all
green, no plugin code touched. All results match the `main` run counts
(41/12/17/7/12/4), confirming the new WP 6.6.x / WC 9.0.x / PHP 8.1 baseline
behaves identically to the tested-up-to versions.

### Tooling defects found and fixed (not plugin defects)

Found at level 0:

1. `check.sh`: the PHP version list was joined into one string (`8.1 8.3`) → false
   "not installed" FAIL. Fixed: line-by-line parsing.
2. `stand.sh stop`: the clean-state proof `pgrep -f 'mysqld|php -S'` matched its own
   command line, so a clean state could never be shown. Fixed: exact-name matching
   (`pgrep -x`); rule recorded in `AGENTS.md`.

Found by pre-flight review before level 1 (all passed `bash -n` / `node --check`):

3. e2e scripts: `ENGLINES[...]` typo vs the defined `ENGINES` → every browser check
   would have thrown a ReferenceError. Fixed in all four scripts.
4. `stand.sh up`: `--wp=latest` was routed into the branch resolver → the `main`
   stand could not boot at all. Fixed: `latest` and exact x.y.z pass through.
5. `stand.sh`: the WooCommerce branch resolver matched the major only (9.0 → 9.9.x).
   Fixed: full major.minor match via the plugin directory API (9.0 → 9.0.4); the WP
   resolver moved to the releases list (6.6 → 6.6.9).
6. `check.sh` archive copied screenshots (binary) into the working area. Fixed:
   tar with binary excludes + a screenshot list.
7. `check.sh`: `--browser=` was dropped by the option parser; level order diverged
   from the proven original (uninstall block before browser scenarios); the output
   directory was not cleaned between runs. All fixed.

Found by the first level 1 start:

8. `check.sh`: `local stand="$1" dir="/tmp/wp-stand-$stand"` — bash expands the whole
   `local` line before assigning, so `$stand` was unbound under `set -u` and the run
   aborted immediately. Fixed in six functions (`$1` used directly, as in the original).

No new tooling defects were found in rounds A and B: the fixes from levels 0
and 1 carried over cleanly to the second stand, the branch-resolved versions,
and the cache scenario.

Conclusion: **0.4.1 passes levels 0, 1 and 2 in full, without a single code
change** — on the tested-up-to versions (`main`: WP 7.1.2 / WC 11.1.2 / PHP 8.3),
on the new platform baseline (`min`: WP 6.6.9 / WC 9.0.4 / PHP 8.1 / ru_RU), and
under a real WP Super Cache setup (24/24). The manual user verification (5/5 on
Storefront 4.6.2) completes the picture. The remaining optional item is a WebKit
engine pass, which does not gate anything. The verified-build claim of the
CHANGELOG is now backed end to end; the only caveat left is the platform
minimums, which live in the docs but not yet in the plugin headers (they ship
with 0.5.0).

## Выявленные дефекты и исправления

| № | Дефект | Причина | Исправление |
| --- | --- | --- | --- |
| 1 | **Статический шорткод показывает только 1 товар** (`products=«214,217»`) | В коде использовался `explode( ',', $args['products'] )` с приведением к `(int)`. Русские кавычки «ёлочки» (`\xc2\xab`) в начале строки ломали приведение первого числа: `(int)"«214"` давало 0, а второе число `(int)"217»"` считывалось | В `Storage::normalize_ids()` и `Shortcodes::table()` извлечение чисел переведено на `preg_match_all('/\d+/', ...)` (и в JS на `raw.match(/\d+/g)`). Любые кавычки (русские, лапки, прямые), пробелы и разделители теперь корректно парсятся |
| 2 | **Изображение товара наплывает на название и цену** (на скриншоте фото процессора закрывало текст) | У `.rvn-product-image-link` не было `overflow: hidden` и фиксированной высоты, а `.rvn-product-card` не имел flex-колонки. Крупные квадратные фото товаров вылезали за пределы контейнера вниз, накрывая название и кнопки | `.rvn-product-card` получил `display: flex; flex-direction: column`. Контейнер ссылки получил строгие `height: 140px; max-height: 140px; overflow: hidden; padding: 4px`. Название товара размещено строго под миниатюрой, а блок цены и покупки прижат к низу карточки через `margin-top: auto` |
| 3 | **Стрелка слайдера искажается при наведении (синий овал) и исчезает на краях** | Глобальные стили кнопок темы Storefront переопределяли фон на синий и добавляли внутренний отступ `padding`, вытягивая кнопку в овал. Свойство `visibility: hidden` при `disabled` полностью прятало стрелку, из-за чего клик попадал по товару под ней | Кнопки стрелок получили класс `.rvn-table-arrow`, чистый центрированный SVG-шеврон вместо текстовых `‹`/`›`, сброс стилей с `!important`, круглую форму `36x36px` и белый фон. При `:disabled` стрелки остаются видимыми на месте с пониженной прозрачностью (`opacity: 0.35`) и `cursor: not-allowed` |
| 4 | **Таблица прыгает вниз и вверх при переключении вкладок браузера** | Событие `visibilitychange` вызывало `load()`, которое показывало плашку «Загружаем список сравнения…» над таблицей, сдвигая её вниз, а затем скрывало обратно | В `table.js` добавлена проверка `sameIds()`: если список ID не изменился, повторный запрос не выполняется. Плашка загрузки теперь показывается только при первой отрисовке (когда `state.data === null`), фоновые обновления таблицы происходят бесшовно |
| 5 | **На десктопе видно только 3 колонки вместо 5** | Функция `resizeColumns()` сравнивала ширину контейнера таблицы с брейкпоинтом 1024 px. В Storefront контентная область центрирована (~950 px), поэтому условие `<= 1024` срабатывало даже на экранах 1920 px | Точки перехода теперь ориентируются на фактическую ширину экрана (`window.innerWidth || width`), позволяя выводить заданные 5 колонок на десктопе |
